# 开发过程与关键决策

## 背景

本项目以原有 Python/NiceGUI 劳动法智能体演示版为功能参考，在三天冲刺范围内重构为
HarmonyOS 原生应用。开发主要使用 DevEco Studio、ArkTS/ArkUI 和 Codex
（GPT-5.6 Sol）协作完成，由使用者负责产品取舍、视觉选择和真机验收。

目标不是机械移植 Python GUI，而是在时间约束内保留最有参赛价值的用户闭环：

```text
提出劳动法律问题 → 本地检索依据 → 模型分析 → 核对引用
                    ↘ 案件梳理 → 卷宗 → 报告
```

## 关键产品取舍

### 不部署项目服务器

参赛 MVP 直接调用用户配置的模型 API。这样只需要一个 HAP，不需要维护后端、域名、
数据库或云主机。代价是模型服务商会接收用户主动提交的咨询内容，因此界面和文档必须
明确告知数据流向。

### 暂不使用向量数据库

原 Python 项目具有向量检索和 GraphRAG 实验代码，但 HarmonyOS 参赛版采用本地 JSON
和加权文本检索。原因是三天内更容易编译、调试和离线发布，也无需端侧模型或云检索
服务。后续可在不改变 UI 的前提下替换 `KnowledgeService`。

### 全量机械收录，暂不清洗

为了突出覆盖面，当前索引收录全部 2790 个源文件。开发阶段明确不做：

- 失效法规清理；
- PDF/DOCX 重复消除；
- 历史版本合并；
- 地方低相关公文筛除；
- 图片和扫描件 OCR。

因此每条结果都展示来源和状态，并持续提示用户核对官方最新文本。

### 先支持高价值附件格式

首版只支持 TXT、MD、DOCX。它们能够覆盖劳动合同、通知、情况说明等主要演示材料，
而 PDF 版式、图片 OCR 和损坏压缩包会显著增加开发与稳定性风险。

## AI 辅助开发方式

AI 在本项目中用于：

- 阅读原 Python 代码并制作功能映射；
- 生成 ArkTS 实现、错误处理和转换脚本；
- 分析构建日志、模拟器/真机现象和崩溃原因；
- 根据使用者反馈迭代 UI、交互和应用图标；
- 整理构建、验收和开源文档。

人类开发者负责：

- 决定功能范围、竞赛策略和隐私边界；
- 在华为开发者平台登录并安装官方工具；
- 选择模拟器/真机配置和完成系统授权；
- 输入私有 API Key，并对真实问答结果进行判断；
- 审核视觉方向和最终发布内容。

AI 生成代码不等于已经验证。每项关键改动都应经过编译，涉及设备能力时还应经过
模拟器或真机验证。
